# ADR-059 — Speculative-application route directory

- **Date:** 2026-10-29
- **Status:** Accepted product direction; implementation is staged through M0–M8.
- **Goal:** Refocus the product into a worldwide directory of video-game companies whose official application route explicitly accepts speculative applications, rather than a standard vacancy finder.
- **Definition:** A speculative application has no specific advertised job and no deadline, and is available to people who do not fit current listings. The owner researches and submits each application manually; the product never sends applications or messages.
- **Qualifying evidence:** Fetch the actual official studio page or its own ATS page. The page must explicitly invite applications without a particular vacancy and have no deadline/closing date; the route must be reachable now. Aggregators are discovery hints only. Internship/graduate schemes, generic “see our jobs” pages, agencies, and search snippets do not qualify.
- **Route types:** `dedicated-page`, `ats-posting`, `email-invite`, and separately-labelled `talent-community`. Store no email addresses; link to the official page.
- **Lifecycle:** `candidate` is auto-detected but unverified; `verified` requires a human-level evidence check; `needs-review` marks failed or changed evidence; `stale` means no re-verification within 90 days. Never auto-delete a verified route. A failed fetch cannot establish closure.
- **Evidence/data contract:** Store route URL, route type, matched phrase category, a short original paraphrase, content hash, and check dates plus the versioned route fields defined in M2. Do not copy page text. Fail closed on missing evidence, unsafe URLs, unsupported assertions, or incomplete records.
- **Research method:** Fetch every candidate page before proposing it as verified. Respect robots.txt and rate limits, identify the user agent, use public pages only, and never log in or bypass access controls/bot protection. A blocked or login-walled route becomes `needs-review`.
- **Existing code:** Retain standard-role listing code and tests for compatibility, but M1 introduces `FEATURES.roleExplorer = false` and hides role counts and role-finder wording when disabled. The discovery workflow remains manual-only unless a later milestone is explicitly approved.
- **Publishing:** Reuse the existing same-repository GitHub Pages workflow and artifact/privacy checker for M7. PR #9 is already merged; do not attempt to close or undo that merged history. Keep `scripts/check-pages-artifact.mjs` and its tests.
- **Conflict reduction:** New ADRs live as separate files under `docs/decisions/`; new changelog fragments live under `changelog.d/`. `STATUS.md` remains the sole source of current milestone, branch, PR, verification, and next-action state.
- **Approvals:** Work milestone-by-milestone in one PR per milestone; push to the milestone branch without waiting for a second approval. The owner merges. No schedule enablement, publication, repository-visibility change, force-push/history rewrite, branch deletion, secrets change, workflow-permission expansion, or new dependency without explicit approval. M5 may edit discovery workflows but must retain manual dispatch.
- **M0 definition of done:** Confirm the merged state and exact-head CI for PRs #7/#8/#9; retain the existing Pages artifact guard; publish this ADR and its changelog fragment; update `STATUS.md` in the same commit; open one M0 PR with CI evidence. Main-head CI after that PR is merged remains part of owner-controlled closeout.
- **Validation:** Review the full change set, ensure no personal data, email addresses, secrets, or copied source-page text are introduced, and require the repository's existing CI on the exact M0 PR head.
- **Rollback:** Revert the focused M0 documentation commit/PR. Do not revert or rewrite the already-merged #7–#9 work; the new product direction is implemented incrementally in M1–M8.
